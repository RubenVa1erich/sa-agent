# Правила работы с артефактами

## Где хранятся

Всё — внутри `projects/<project_id>/outputs/<тип>/`. Файл вне папки проекта не
принадлежит ни одному проекту — так не делать.

## Именование

`<project_id>_<объект>_<тип>_v<N>.<ext>` — объект в `snake_case`, латиницей.

| Тип | Папка | Пример |
|---|---|---|
| Декомпозиция | `requirements/` | `loans_early_repayment_reqs_v1.md` |
| ФТ / ТЗ | `specs/` | `loans_early_repayment_spec_v1.md` |
| REST | `api/` | `loans_repayment_service_openapi_v1.yaml` (+ `_api_v1.md` описание) |
| События | `api/` | `loans_repayment_events_asyncapi_v1.yaml` |
| gRPC | `api/` | `loans_scoring_v1.proto` (версия пакета внутри) |
| Диаграмма | `diagrams/` | `loans_early_repayment_sequence_v1.puml` |
| Интеграция | `integrations/` | `loans_bki_integration_v1.md` |
| Анализ влияния | `impact/` | `loans_cr042_impact_v1.md` |
| Ревью | `reviews/` | `loans_early_repayment_spec_v1_review.md` (без своей версии — привязан к версии документа) |
| ADR | `decisions/` | `0007-2026-09-30-async-status-updates.md` (MADR: сквозной номер + дата) |
| Тест-кейсы | `tests/` | `loans_early_repayment_tests_v1.md` |
| Модель данных | `data/` | `loans_repayment_datamodel_v1.md` (+ `loans_repayment_ddl_v1.sql`, ERD в `diagrams/`) |
| Дайджест встречи | `meetings/` | `loans_2026-09-30_grooming_meeting.md` (без версии — привязан к дате встречи) |
| Статус проекта | `reviews/` | `loans_status_2026-09-30.md` (только по запросу; обычно — в сообщении) |

Confluence-версия лежит рядом: тот же путь, расширение `.confluence.md`.

**Экспорт в Word / Excel** (внешние скиллы `docx` / `xlsx`) — тоже рядом с исходником, то же
имя, другое расширение: `loans_early_repayment_spec_v1.docx`, `loans_early_repayment_tests_v1.xlsx`,
`loans_early_repayment_tests_v1.testrail.csv`. Для статуса и трассировки — в `reviews/`:
`loans_trace_2026-10-01.xlsx`. Экспорт — производная: правки вносятся в `.md`, затем экспорт
повторяется. Не версионируется отдельно (версия — от исходника).

## Версионирование

- Первая выдача — `_v1`.
- Существенные изменения (новые/удалённые требования, изменение контракта) — **новый
  файл `_v<N+1>`**, старый не трогать. Записать в «Историю изменений» что и почему поменялось.
- Мелкие правки черновика, который ещё не отдан команде — можно в текущей версии,
  **только если аналитик так сказал**. По умолчанию — спросить одним вопросом:
  «Правлю v1 или делаю v2?» (если это не очевидно из контекста).
- **Явное указание аналитика о версии главнее этих умолчаний** — для любых изменений,
  включая существенные. «Правь в текущей» → правишь текущую и пишешь строку в «Историю
  изменений» этой же версии; «сделай новую» → `_v<N+1>`. Не переспрашивай и не
  «исправляй» его решение новой версией.
- Перед созданием новой версии — найди последнюю существующую (Glob по префиксу).
- ADR не версионируется: решение меняется новым ADR со статусом «Заменяет ADR-NNNN»,
  у старого статус меняется на «Заменено ADR-MMMM».

## Запись больших документов — по частям

Документ длиннее ~300 строк (ТЗ, интеграционная спека, анализ влияния крупного CR, большой
OpenAPI) одним вызовом Write рискует оборваться на середине, и обрыв легко не заметить.
Поэтому:

1. **Скелет:** Write с шапкой, «Историей изменений» и всеми заголовками разделов; под каждым —
   маркер `<!-- TODO-SECTION -->`.
2. **Наполнение:** по одному-два раздела за вызов Edit, заменяя маркер содержимым.
3. **Проверка полноты:** Grep `TODO-SECTION` по файлу — должно быть 0 совпадений; для YAML —
   файл заканчивается последним блоком `components`, а не обрывком.
4. Только после этого — самопроверка, `.confluence.md` и `trace.md`.

Для коротких артефактов (декомпозиция, ADR, одна диаграмма, ревью) — обычный Write.

## Шапка документа (для .md-артефактов)

```markdown
# <Название>

| | |
|---|---|
| Проект | <project_id> |
| Версия | v1 |
| Статус | Черновик / На ревью / Согласовано |
| Дата | ГГГГ-ММ-ДД |
| Автор | <аналитик> (черновик — SA Agent) |
| Источники | <входные файлы, тикеты, БТ-ID> |

## История изменений
| Версия | Дата | Что изменено |
|---|---|---|
| v1 | ГГГГ-ММ-ДД | Первая версия |
```

## Блок для ревьюеров

Крупные документы (спека, интеграция, анализ влияния) заканчиваются разделом
«**Для ревью**», в котором для каждой роли — что проверить и где:

- **Архитектор** — ключевые решения, НФТ, интеграции, риски (ссылки на разделы/ADR)
- **Разработка / тимлид** — контракты, обработка ошибок, edge cases, изменения моделей данных
- **QA** — критерии приёмки, где их недостаточно; ссылка на тест-кейсы, если есть
- **PM / бизнес** — трассировка к бизнес-требованиям, что вошло / не вошло в скоуп

Коротко, 1–3 пункта на роль.

## Трассировка (`trace.md`)

После создания/обновления артефакта с требованиями, API или тестами — обнови
`projects/<project_id>/trace.md` (формат — в шаблоне проекта). Строка на системное требование:
`БТ → СТ → API/событие → Диаграмма → Тест → Статус`. Неизвестные ячейки — `—`.
Новые номера → обнови «Счётчики» (правило — `conventions.md`, «Как выдавать номера»).

## Сообщение аналитику после сохранения

```
✅ Сохранено: `projects/<id>/outputs/specs/<file>_v1.md` (+ `.confluence.md`)
Что внутри: <1 строка>
Допущения: <до 5, кратко> 
Открытые вопросы: <N> — в разделе «Открытые вопросы»
Дальше: <1–2 логичных следующих шага, например «проверить качество» или «сгенерировать sequence»>
```

## Никогда не удаляй

Не удаляй файлы в `projects/`. Устаревшие требования помечаются статусом «Устарело»
с причиной, а не удаляются. Если аналитик просит удалить — выполни, но только по явной просьбе.
