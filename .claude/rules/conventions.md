# Соглашения по умолчанию

Действуют, **если в `project_context.md` не указано иное**. Проектные соглашения
всегда приоритетнее. Если применил умолчание в новом проекте — упомяни это один раз.

## Язык

- Артефакты — на языке из `project_context.md` (поле «Язык артефактов»), по умолчанию **русский**.
- Всегда на английском: имена полей, ресурсов, эндпоинтов, событий, топиков, enum-значений,
  имена файлов, идентификаторы в диаграммах (подписи — на языке артефакта).
- Термины без устоявшегося перевода не переводить (idempotency key, retry, DLQ, backoff).

## Нумерация требований

| Тип | Префикс | Пример |
|---|---|---|
| Бизнес-требование (входное) | `БТ-` | БТ-003 |
| Функциональное системное | `ФТ-` | ФТ-012 |
| Нефункциональное | `НФТ-` | НФТ-004 |
| Ограничение | `ОГР-` | ОГР-001 |
| Открытый вопрос | `ОВ-` | ОВ-007 |
| Тест-кейс | `ТК-` | ТК-021 |
| ADR | `ADR-` | ADR-0007 |

- Номера **сквозные в рамках проекта** и не переиспользуются (в том числе номера
  устаревших требований).
- Если в project_context задан другой формат (например, `SR-`, `FR-`) — использовать его.
- «СТ» в `trace.md` — общее название системного требования (ФТ / НФТ / ОГР), не отдельный префикс.

### Как выдавать номера — единое правило для всех скиллов

Источник истины — раздел **«Счётчики»** в `trace.md` (последний выданный номер по каждому префиксу).

1. **Перед выдачей** прочитай счётчик и сверь с фактом: Grep по префиксу (`ФТ-\d+`, `ТК-\d+`…)
   в `outputs/` и `trace.md`. Если в файлах есть номер больше счётчика (кто-то правил
   вручную) — продолжай от максимума из файлов и скажи об этом одной строкой.
2. **Выдавай** подряд, начиная со «счётчик + 1».
3. **После сохранения артефакта** обнови «Счётчики» вместе с остальными строками `trace.md`.
   Артефакт с новыми номерами без обновлённого счётчика — незавершённая задача: следующий
   скилл выдаст те же номера повторно.
4. ADR — так же, по счётчику `ADR`; сверка — по именам файлов в `outputs/decisions/`.
5. Новая версия документа (`_v<N+1>`) **сохраняет** существующие номера; новые номера — только
   для новых требований.

## Формулировка требований

- ФТ: **«Система должна <действие> <объект> [<условие>]»** — одно утверждение.
- Критерии приёмки — нумерованный список проверяемых утверждений: `AC-1: ...`, `AC-2: ...`.
- Приоритет — **MoSCoW** (Must / Should / Could / Won't).
- НФТ — всегда с метрикой и условиями измерения: «p95 времени ответа ≤ 300 мс при 200 RPS».

## REST API

| Аспект | Умолчание |
|---|---|
| Спецификация | OpenAPI **3.1**, YAML |
| Поля JSON | `camelCase` |
| Пути | существительные во мн. числе, `kebab-case`: `/v1/loan-applications/{applicationId}` |
| Версионирование | мажорная версия в пути `/v1`; ломающие изменения → `/v2` |
| Даты/время | ISO 8601, UTC, `format: date-time` (`2026-09-30T12:00:00Z`); дата без времени — `format: date` |
| Деньги | объект `{ amount: string (decimal), currency: string (ISO 4217) }`; не float |
| Идентификаторы | строки (UUID), не автоинкремент наружу |
| Ошибки | **RFC 9457 Problem Details** (`application/problem+json`): `type`, `title`, `status`, `detail`, `instance` + `code` (машиночитаемый) + `errors[]` для валидации |
| Идемпотентность | заголовок `Idempotency-Key` для небезопасных POST (создание, платёжные операции) |
| Пагинация | cursor-based: `limit`, `cursor` → `nextCursor`; offset — только если явно нужно |
| Enum | `UPPER_SNAKE_CASE` |
| Nullable | явно: `type: [string, "null"]`; отсутствие поля ≠ null — описать семантику |
| Трассировка запросов | заголовок `X-Request-Id` (или корпоративный из project_context) |

## События (Kafka / RabbitMQ)

| Аспект | Умолчание |
|---|---|
| Спецификация | AsyncAPI **3.0**, YAML |
| Имя события | прошедшее время, `PascalCase`: `LoanApplicationApproved` |
| Kafka-топик | `<домен>.<сущность>.<событие>.v<N>` в `kebab-case`: `loans.application.approved.v1` |
| RabbitMQ | exchange `<домен>.events` (topic), routing key `<сущность>.<событие>` |
| Конверт | CloudEvents-подобный: `id`, `type`, `source`, `time`, `specVersion`, `data`; + `correlationId` |
| Ключ партиционирования | ID агрегата (порядок событий по одной сущности) |
| Доставка | at-least-once → потребитель идемпотентен (дедупликация по `id`) |
| Ошибки | retry с backoff → DLQ/DLT; указать число попыток |
| Совместимость | только обратно совместимые изменения внутри `v<N>` (добавление опциональных полей) |

## gRPC

- proto3, пакет `<company|domain>.<service>.v1`
- Сервис `PascalCase` + `Service`, RPC — глаголы `PascalCase`, поля — `snake_case` (стиль proto)
- Ошибки — стандартные gRPC status codes + `google.rpc.ErrorInfo` в details
- Deadlines указывать явно в спецификации

## Диаграммы

- **PlantUML**. C4 — через `!include <C4/C4_Container>` (stdlib PlantUML).
- Имена участников — латиницей (alias), подписи — на языке артефакта.
