# Разбор встречи

**Вход:** заметки / транскрипт / пересказ (в чате или файл в `inputs/`) + `project_context.md`
+ `trace.md` (чтобы узнать ответы на существующие ОВ).
**Выход:** `outputs/meetings/<project_id>_<ГГГГ-ММ-ДД>_<тема>_meeting.md` + предложенные
действия по артефактам (выполняются после подтверждения).

Сначала результат (дайджест), потом — один вопрос «Что из действий выполнить?».

## Алгоритм

1. Прочитай вход. Дату встречи и участников бери из входа; если их нет — `[TODO]`,
   не подставляй сегодняшнюю дату молча.
2. Прочитай открытые ОВ из `trace.md` и ключевые допущения из последних артефактов —
   ответы на них часто звучат на встрече без ссылки на номер.
3. Разложи содержание по категориям:

   | Категория | Признаки во входе | Куда пойдёт |
   |---|---|---|
   | **Решение** | «решили», «договорились», «идём через …», «выбрали» | архитектурно значимое → кандидат в ADR (`decision-log`); локальное → только в дайджест |
   | **Ответ на ОВ** | ответ на вопрос из `trace.md` или на допущение | `open-questions`, режим «закрыть» |
   | **Новое / изменённое требование** | «ещё нужно», «теперь должно», «убираем» | если меняет существующие артефакты → кандидат в CR (`impact-analysis`); новое → в `requirements-decompose` |
   | **Новый вопрос** | «надо уточнить», «не знаем», «X проверит» | новый ОВ (`open-questions`) |
   | **Договорённость** | «Иван пришлёт», «до пятницы» | только в дайджест — агент не трекер задач |
   | **Риск / опасение** | «боимся, что», «а если банк не успеет» | в дайджест; если касается артефакта — в его риски |

   Архитектурно значимое решение — то, которое меняет интеграции, модель данных, контракты,
   распределение ответственности или его дорого отменить. Остальное в ADR не тянуть.

4. **Не достраивай.** Если из заметок неясно, решено или только обсуждалось — это
   «Обсуждали, не решено», а не решение. Исполнителя и срок не придумывай: `[TODO: кто?]`.
   Противоречия внутри заметок («сначала решили A, потом говорили про B») — покажи явно.
5. Сохрани дайджест. Номера новых ОВ пока не выдавай — они появятся при выполнении действий.
6. В сообщении — краткая сводка и пронумерованный список действий:
   ```
   Действия по артефактам:
   1. Закрыть ОВ-004 (отзыв возможен до принятия оффера) → обновит reqs_v1, spec_v1
   2. ADR: «Уведомление банков об отзыве через RabbitMQ»
   3. CR: банки получают причину отзыва → impact-analysis
   4. Новый ОВ к Integrations: SLA банков на приём отзыва
   Выполнить все / выбрать номера?
   ```
   Выполняй выбранное соответствующими скиллами, по одному.

## Формат дайджеста

```markdown
# Встреча: <тема>
| | |
|---|---|
| Проект | <project_id> |
| Дата встречи | ГГГГ-ММ-ДД |
| Участники | <имена / роли> |
| Источник | <файл в inputs/ или «пересказ в чате»> |

## Кратко
<2–4 строки: зачем собирались и главный итог>

## Решения
| # | Решение | Обоснование (если звучало) | Значимость | Действие |
|---|---|---|---|---|
| Р-1 | ... | ... | ADR / локальное | ADR-00NN / — |

## Обсуждали, не решено
- ...

## Ответы на открытые вопросы
| ОВ / допущение | Ответ | Кто ответил | Затронутые артефакты |

## Новые и изменённые требования
| # | Что | Новое / изменение | Действие |

## Новые вопросы
| Вопрос | Кому | Блокирует |

## Договорённости
| Кто | Что | Срок |

## Риски и опасения
- ...

## Неясности в заметках
<что не удалось однозначно интерпретировать>
```

Пустые разделы — убирай (в отличие от спек: дайджест читают быстро).
