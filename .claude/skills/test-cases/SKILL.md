# Генерация тест-кейсов

**Вход:** спецификация (`outputs/specs/`, `outputs/integrations/`) и/или контракт (`outputs/api/`).
**Выход:** `outputs/tests/<project_id>_<объект>_tests_v<N>.md` + обновлённая колонка «Тесты» в `trace.md`.
Тест-кейсы на весь документ — сначала структура (группы и количество кейсов по требованиям).

## Алгоритм

1. Прочитай источник. Составь список проверяемых единиц: каждое ФТ с AC, каждая
   операция API, каждый переход статусной модели, каждый сбойный сценарий интеграции.
2. **Техники** (применяй там, где уместно):
   - Каждый AC → минимум 1 позитивный кейс
   - **Классы эквивалентности** для входных полей
   - **Граничные значения**: min−1, min, max, max+1, пусто, null, 0
   - **Таблица решений** для бизнес-правил с комбинациями условий
   - **Переходы состояний**: каждый допустимый переход + попытки недопустимых
   - **Ошибки API**: каждый код ошибки из контракта — хотя бы один кейс
   - **Идемпотентность / конкурентность**: повтор с тем же ключом, параллельные запросы
   - **Интеграции**: таймаут, 5xx, невалидный ответ, дубль сообщения, недоступность брокера
3. Не генерируй кейсы, которые проверяют одно и то же. Лучше меньше, но с явной целью.
4. Если AC требования неверифицируем — не выдумывай ожидаемый результат, а отметь
   в разделе «Требования без проверяемых AC» (это сигнал для `quality-review`).
5. Номера ТК — по правилу «Как выдавать номера» (`conventions.md`); после сохранения
   обнови колонку «Тесты» и счётчик `ТК` в `trace.md`.
6. Приоритет кейса: наследуется от требования (Must → Высокий), негативные по
   безопасности и деньгам — Высокий.

## Формат

```markdown
# Тест-кейсы: <объект>
<шапка из artifacts.md; Источники: спека vN, контракт vN>

## Покрытие
| Требование | Кейсы | Не покрыто |
|---|---|---|
| ФТ-012 | ТК-001..ТК-004 | — |

## Тестовые данные
<Общие предусловия и данные: пользователи/роли, сущности в нужных статусах, моки внешних систем>

## Кейсы

### ТК-001. <Что проверяем — кратко>
| | |
|---|---|
| Требование | ФТ-012 (AC-1) |
| Тип | Позитивный / Негативный / Граничный / Отказ зависимости / Безопасность |
| Уровень | API / Интеграционный / E2E |
| Приоритет | Высокий / Средний / Низкий |

**Предусловия:** ...
**Шаги:**
1. ...
**Ожидаемый результат:**
- <наблюдаемый результат: код ответа, тело, состояние в БД, опубликованное событие>

## Требования без проверяемых AC
- ...

## Открытые вопросы
```

Для API-кейсов в шагах — конкретный запрос (метод, путь, ключевые поля тела),
в ожидаемом результате — HTTP-код и `code` ошибки.

## Экспорт для QA / TMS

По запросу — только из сохранённого `.md` (сначала кейсы, потом экспорт). Через скилл
`anthropic-skills:xlsx`, файл — рядом с исходником (`artifacts.md` → «Экспорт»).

| Цель | Формат | Колонки |
|---|---|---|
| Excel для QA / ревью | `.xlsx`, лист «Кейсы» + лист «Покрытие» | ID · Название · Требование · Тип · Уровень · Приоритет · Предусловия · Шаги · Ожидаемый результат |
| TestRail | `.testrail.csv` | Title · Section · Priority · Type · Preconditions · Steps · Expected Result · References |
| Zephyr / Allure TestOps / другая TMS | `.csv` | Спроси формат импорта одним вопросом, если его нет в `project_context.md`; запиши его туда после согласия |

- Шаги — одна ячейка, нумерованные строки через перевод строки; ID ТК и ФТ — в отдельных
  колонках (`References` = `ФТ-012`), чтобы в TMS сохранилась трассировка.
- Кодировка CSV — UTF-8 с BOM (иначе Excel и часть TMS ломают кириллицу), разделитель — `,`.
- Колонки TestRail — типовые; если у команды кастомные поля — их маппинг в `project_context.md`.
