# Проектирование API

**Вход:** описание функционала + кто вызывает, что возвращает, какие данные.
**Выход:** файл контракта в `outputs/api/` + опционально `_api_v<N>.md` (человекочитаемое
описание) + `.confluence.md` к нему + обновлённый `trace.md`.

**Крупный** (сервис, 3+ операций, несколько событий) — сначала структура.
**Малый** (один эндпоинт / одно событие) — сразу контракт.

## Шаг 0. Выбор типа контракта

| Ситуация | Тип | Reference |
|---|---|---|
| Синхронный запрос-ответ по HTTP | OpenAPI 3.1 | `references/rest_openapi.md` |
| Событие / сообщение в Kafka или RabbitMQ | AsyncAPI 3.0 | `references/async_events.md` |
| Внутренний синхронный RPC, высокая нагрузка, gRPC в стеке | proto3 | `references/grpc.md` |
| GraphQL, SOAP/WSDL, файловый обмен, webhooks, иное | Общий шаблон | `references/other_contracts.md` |

Если тип не очевиден и не задан в project_context — это архитектурное решение:
предложи варианты кратко (см. `behavior.md`), не выбирай молча.

Коды ошибок и их семантика для всех типов — `references/error_codes.md`.

## Алгоритм

1. Прочитай `project_context.md` (соглашения!) и нужный reference.
2. **Структура (для крупных):**
   - REST: ресурсы, операции `МЕТОД путь — назначение`, ключевые схемы
   - События: список событий, канал (топик/exchange), продюсер → консьюмеры, ключ
   - gRPC: сервис, RPC, основные сообщения
   Плюс замечания по дизайну (п. 4) и ключевые допущения. Жди подтверждения.
3. **Генерация контракта** по reference. Каждое поле: тип, обязательность, nullable,
   формат, ограничения, `description`, `example`. Каждая операция — все релевантные ошибки.
   Крупный контракт (сервис целиком) — по частям: `info`/`paths` скелетом, затем операции
   и `components` через Edit (`artifacts.md` → «Запись больших документов»).
4. **Замечания по дизайну** — выдай отдельным списком в сообщении (и в `.md`-описании):
   - нарушения REST-конвенций / соглашений проекта (глаголы в путях, 200 на ошибку, и т.п.)
   - неоднозначности нейминга (одна сущность — разные имена; `status` vs `state`)
   - отсутствующая идемпотентность, пагинация, версионирование
   - утечка внутренней модели наружу (внутренние ID, технические поля)
   - обратная совместимость, если меняется существующий контракт
5. **Самопроверка** по `quality_bar.md` → «API / события». Проверь, что YAML
   синтаксически валиден (отступы, кавычки у строк с `:`), `$ref` указывают на
   существующие схемы, примеры соответствуют схемам.
6. **Описание `.md`** — делай, если аналитик просил, или если контракт крупный
   (формат — раздел «Операции» из `spec-write/templates/api_focused.md`). Для него — `.confluence.md`.
7. Обнови `trace.md`: колонка «API / событие» у соответствующих ФТ.

## Изменение существующего контракта

1. Прочитай текущую версию из `outputs/api/`.
2. Классифицируй каждое изменение: **ломающее** / **обратно совместимое** / **расширение**
   (правила — в reference по типу).
3. Ломающее → предложи варианты: новая мажорная версия / параллельное поле с deprecation /
   согласование миграции потребителей. Не принимай решение сам.
4. Сохрани как `_v<N+1>`, в описании — таблица изменений с классификацией.
