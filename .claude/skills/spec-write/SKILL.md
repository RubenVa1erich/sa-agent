# Написание ФТ / ТЗ

**Вход:** требования (файл декомпозиции, список, описание) + `project_context.md`.
**Выход:** `outputs/specs/<project_id>_<объект>_spec_v<N>.md` + `.confluence.md` + `trace.md`.
**Крупный артефакт** — сначала структура.

## Выбор шаблона

1. Если в `project_context.md` указан шаблон — он.
2. Если в `templates/` есть файлы, кроме default и api_focused (эталон аналитика) и
   аналитик на него ссылался — он. **Воспроизводи структуру и стиль эталона**: разделы,
   порядок, формат таблиц, манеру формулировок.
3. Иначе:
   - `templates/default.md` — фича/процесс с бизнес-логикой, UI, статусами
   - `templates/api_focused.md` — задача в основном про контракт сервиса/интеграцию
   Скажи, какой выбрал, одной строкой.

## Алгоритм

1. Если входа — «сырой» текст без декомпозиции, сначала выполни декомпозицию по
   `requirements-decompose` (внутренне, без отдельного файла, если аналитик не просил).
2. **Структура на согласование:** шаблон, список разделов с 1 строкой содержания,
   количество ФТ/НФТ, ключевые допущения. Жди подтверждения (если не сказано «без согласования»).
3. **Генерация** — по частям: скелет, затем разделы через Edit (`artifacts.md` →
   «Запись больших документов»). Заполни все разделы шаблона. Раздел, для которого нет данных — не удаляй,
   а оставь с `[TODO: ...]` — пустые разделы видны ревьюерам.
4. Требования: по `conventions.md` (ФТ-NNN, «Система должна…», AC-списком, MoSCoW).
   Номера — по правилу «Как выдавать номера» (`conventions.md`); если есть декомпозиция —
   сохраняй её номера, новые выдавай только недостающим.
5. Если в спеке есть поток взаимодействия / статусная модель / модель данных —
   **встрой PlantUML-код** в раздел (блок ```plantuml) и сохрани отдельный `.puml`
   по `diagram-generate`.
6. Термины — из «Глоссария» `project_context.md`; новые доменные понятия — в глоссарий
   документа (если в шаблоне есть) и предложением в сообщении: «Добавить в глоссарий проекта: …?»
7. «Открытые вопросы» — все TODO и допущения. «Для ревью» — по `artifacts.md`.
8. **Самопроверка** по `quality_bar.md`.
9. Сохрани `.md`, сгенерируй `.confluence.md` (скилл `confluence-export`), обнови `trace.md`
   и «Счётчики». Если аналитик просил Word — после этого `.docx` из `.md`
   (`anthropic-skills:docx`, см. CLAUDE.md → «Внешние скиллы»).

## Правила формулировок

- Одно требование = один абзац «Система должна…». Условия — в начало:
  «При получении статуса REJECTED система должна…».
- Бизнес-правила с вариантами — таблицей решений, а не вложенными «если».
- Валидации — таблицей: поле | правило | ошибка.
- Статусы — таблицей переходов + state-диаграмма.
- Не дублируй одно требование в двух разделах — ссылайся по ID.

## Шаблоны

- `templates/default.md`
- `templates/api_focused.md`
- Свой эталон: положи файл в `templates/` и скажи агенту «используй шаблон <имя>»
  или впиши в project_context.
