# Проверка качества спецификации

**Вход:** текст спецификации (файл в `outputs/` или `inputs/`, либо в чате). Может быть
OpenAPI/AsyncAPI/proto.
**Выход:** `outputs/reviews/<имя_проверяемого_файла>_review.md` + сводка в сообщении.
Малый артефакт — сразу результат. Исходный документ **не правится**, пока аналитик не попросит.

## Алгоритм

1. Прочитай документ, `project_context.md`, `references/quality_criteria.md`.
2. Пройди по **каждому требованию / операции / полю** и примени критерии
   (А — атомарность, О — однозначность, В — верифицируемость, П — полнота,
   С — согласованность, Т — трассируемость, API — API-специфичные, СП — соответствие соглашениям проекта).
3. Затем — проверки уровня документа: противоречия между разделами, пропущенные
   сценарии, недостающие разделы, неописанные статусы.
   **Термины** — по «Глоссарию» в `project_context.md`: одно понятие под разными именами,
   синоним вместо термина из глоссария, доменный термин без определения → критерий С.
   Пустой глоссарий — не проблема документа; скажи об этом в «Не проверено».
4. Каждой проблеме — **серьёзность**:
   - **Блокер** — разработка/тестирование невозможно или будет сделано неправильно
   - **Важно** — высокий риск разночтения / дефекта
   - **Замечание** — стиль, ясность, мелочи
5. Каждой проблеме — **конкретная рекомендация**, по возможности готовой переформулировкой.
6. Не придумывай проблем ради количества. Если раздел хороший — не упоминай его.
   Сомнительное (зависит от контекста, которого нет) — формулируй как вопрос.

## Формат отчёта

```markdown
# Ревью: <документ> (v<N>)
Дата: ... | Проверено: <что именно> | Не проверено: <что и почему>

## Итог
Блокеров: N · Важных: N · Замечаний: N
Вердикт: Готово к передаче / Готово после исправления блокеров / Требует доработки
<2–3 строки: главные проблемы>

## Проблемы

| # | Где | Критерий | Серьёзность | Проблема | Рекомендация |
|---|---|---|---|---|---|
| 1 | ФТ-012 | О | Важно | «быстро» без метрики | «...в течение 2 с (p95)...» |

## Пропущенные сценарии и edge cases
- ...

## Вопросы к автору
- ...

## Что сделано хорошо
<1–3 пункта, кратко — полезно при ревью чужого документа>
```

Сортировка таблицы: сначала блокеры, внутри — по порядку в документе.

## После ревью

Предложи: «Исправить в новой версии документа?» — если это документ из `outputs/`,
создаётся `_v<N+1>` с исправлениями и записью в «Истории изменений». Спорные
исправления (меняющие смысл) — не применять без подтверждения.
