# Критерии проверки качества

## А — Атомарность
- Одно требование = одно утверждение = один проверяемый результат.
- Сигналы нарушения: «и», «или», «а также», «в том числе», перечисления действий
  через запятую, несколько «должна» в одном требовании.
- Исключение: «и» внутри объекта («фамилия и имя» как один атрибут отображения).

## О — Однозначность
Стоп-слова (без метрики — проблема):
*быстро, мгновенно, своевременно, оперативно, удобно, интуитивно, понятно, просто,
гибко, надёжно, безопасно, эффективно, оптимально, современный, достаточно,
значительный, большой, много, мало, минимальный, максимальный (без числа),
по возможности, по необходимости, при необходимости, как правило, обычно, в основном,
и т.д., и т.п., и прочее, и др., поддерживать (без уточнения чего), обрабатывать
(без уточнения как), корректно, правильно, соответствующий, актуальный, некоторые, разные.*

Также:
- Местоимения с неясным референтом («он», «данная сущность», «этот статус»)
- Пассив без субъекта («данные передаются» — кем? куда?)
- Синонимы одной сущности (заявка / запрос / application)
- Неопределённые сроки («в течение дня» — календарного? рабочего? с какого момента?)
- Часовой пояс для времени и дат

## В — Верифицируемость
- Есть AC, по которому можно получить однозначное «прошло / не прошло».
- AC описывает наблюдаемый результат (ответ API, состояние в БД, событие, UI), а не намерение.
- НФТ — с метрикой, условиями и способом измерения.

## П — Полнота
- Негативные сценарии: невалидный ввод, нет прав, не найдено, конфликт состояния, повтор.
- Граничные значения: 0, пусто, null, максимум, ровно на границе.
- Зависимости: недоступность, таймаут, частичный ответ.
- Конкурентность.
- Жизненный цикл данных: создание, изменение, архивация, удаление, сроки хранения.
- Все статусы статусной модели достижимы и имеют выход (или являются финальными).
- Роли и права для каждой операции.
- Разделы шаблона не пусты (или явно помечены «не применимо» с причиной).

## С — Согласованность
- Одно поле — один тип, формат, обязательность во всех разделах и в контракте.
- Требования не противоречат друг другу и `project_context.md`.
- Диаграммы соответствуют тексту (участники, порядок, статусы).
- Нумерация без дублей и пропусков, ссылки на ID существуют.

## Т — Трассируемость
- У требования есть источник (БТ, CR, тикет, регуляторика).
- Понятно, зачем требование (цель/бизнес-правило).
- Требование без источника — не ошибка само по себе, но вопрос «откуда?».

## API — специфичные проверки
- Для каждой операции перечислены коды ошибок и условия возникновения.
- Нет 200 с ошибкой в теле; бизнес-ошибки отличимы от ошибок формата.
- Каждое поле: тип, required, nullable, формат, ограничения, пример.
- Семантика «поле отсутствует» vs «null» vs «пустая строка» определена (особенно в PATCH).
- Идемпотентность небезопасных операций (Idempotency-Key, поведение при повторе).
- Версионирование и правила совместимости указаны.
- Пагинация для списков; лимиты.
- Деньги не float; даты с часовым поясом.
- Enum: полный список значений и смысл каждого; поведение при неизвестном значении.
- Аутентификация и авторизация (роли/scopes) описаны.
- ПДн: какие поля, маскирование в логах.
- События: ключ партиционирования, гарантии доставки, дедупликация, DLQ.
- Внешние вызовы: таймауты, retry, что при неизвестном результате.

## СП — Соответствие соглашениям проекта
- Нейминг, формат ошибок, нумерация, шаблон — по `project_context.md` / `conventions.md`.
