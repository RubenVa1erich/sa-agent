# Интеграционная спецификация

**Вход:** контекст систем, направление интеграции, какие данные передаются.
**Выход:** `outputs/integrations/<project_id>_<система>_integration_v<N>.md` + `.confluence.md` +
sequence `.puml` в `outputs/diagrams/` + (если нужен) контракт в `outputs/api/` + `trace.md`.
**Крупный артефакт** — сначала структура.

## Алгоритм

1. Прочитай `project_context.md` и `references/integration_patterns.md`.
2. **Определи паттерн** по таблице выбора в reference. Если выбор — открытое
   архитектурное решение, предложи 2–3 варианта с компромиссами и не выбирай молча.
3. **Структура на согласование:** участники, паттерн, список сценариев (основной +
   ошибочные), что пойдёт в контракт, ключевые допущения.
4. **Генерация** по шаблону `templates/integration-spec.md`, по частям — скелет, затем
   разделы через Edit (`artifacts.md` → «Запись больших документов»). Обязательно:
   - sequence для основного сценария **и** хотя бы для одного сбойного (таймаут / ошибка партнёра)
     — по `diagram-generate`, встроенным кодом + отдельный файл
   - таблица ошибок: что может пойти не так → как обнаруживаем → что делаем
   - таймауты, retry-политика, идемпотентность — с конкретными значениями или `[TODO]`
   - риски и требования к надёжности
   - требования к контракту: версионирование, обратная совместимость, кто владеет контрактом
5. Если контракт на нашей стороне новый — предложи сгенерировать его (`api-design`).
   Если контракт внешний (API партнёра) — описываем, как мы его используем, и маппинг полей.
6. **Самопроверка** по `quality_bar.md` + чек-лист надёжности из reference.
7. Сохрани, `.confluence.md`, `trace.md`.

## Маппинг данных

Если данные преобразуются между системами — обязательная таблица:

| Наше поле | Поле партнёра | Преобразование | Обязательность | Примечание |
|---|---|---|---|---|

Отдельно отметить: справочники/enum (как маппятся коды), часовые пояса, форматы сумм,
кодировки, обрезка строк по длине.
