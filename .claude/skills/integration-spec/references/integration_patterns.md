# Паттерны интеграции

## Выбор паттерна

| Паттерн | Когда | Минусы |
|---|---|---|
| **Синхронный REST/gRPC** | Нужен ответ сразу для продолжения сценария; короткая операция (< 1–2 с) | Временная связность: партнёр упал → мы упали; каскадные таймауты |
| **Async запрос + callback / webhook** | Операция у партнёра длительная; партнёр умеет вызывать нас | Надо принимать входящие вызовы, аутентифицировать их, обрабатывать потерю callback |
| **Async запрос + polling статуса** | Длительная операция; партнёр не умеет callback | Задержка, нагрузка от поллинга; нужна стратегия интервалов и таймаут ожидания |
| **Событие (Kafka / RabbitMQ)** | Уведомить других о факте; несколько потребителей; развязка по времени | Eventual consistency; сложнее отладка; нужна идемпотентность |
| **Команда через очередь** | Выполнить действие асинхронно, надёжно, с буферизацией пиков | Нужен канал ответа/статуса |
| **Файловый обмен** | Пакетные объёмы, регламентный обмен, legacy / банки / регуляторы | Задержка, сложная обработка частичных ошибок, дубли |
| **CDC** | Репликация изменений БД в другие системы без изменения кода источника | Привязка к схеме БД источника |

## Надёжность — чек-лист

- [ ] **Таймауты**: connect и read — конкретные значения. Общий бюджет времени сценария ≥ сумма таймаутов с учётом retry.
- [ ] **Retry**: какие ошибки ретраим (5xx, таймаут, 429), какие нет (4xx); число попыток; backoff (экспоненциальный + jitter).
- [ ] **Идемпотентность**: повтор безопасен? Чем обеспечен (ключ, ID операции у партнёра)?
- [ ] **Неизвестный результат** (таймаут после отправки): как узнаём итог — запрос статуса, сверка, callback?
- [ ] **Circuit breaker / деградация**: что делает наша система, пока партнёр недоступен (очередь, отказ пользователю, fallback)?
- [ ] **Гарантия доставки событий**: outbox, at-least-once, дедупликация.
- [ ] **Порядок**: важен ли; как обеспечен.
- [ ] **Сверка (reconciliation)**: для денег и статусов — регламентная сверка с партнёром, кто разбирает расхождения.
- [ ] **Rate limits** партнёра и наш ожидаемый RPS.
- [ ] **Безопасность**: аутентификация (mTLS, OAuth2 client credentials, подпись), шифрование, ПДн в логах.
- [ ] **Наблюдаемость**: correlation ID сквозь системы, метрики ошибок/латентности, алерты.
- [ ] **Окружения**: тестовый контур партнёра, тестовые данные.

## Требования к контракту

- Кто владелец контракта; где он лежит; как согласуются изменения
- Версионирование: схема версий, срок поддержки старой версии, уведомление о deprecation
- Правила совместимости (см. api-design/references)
- Толерантность потребителя: игнорировать неизвестные поля, обрабатывать неизвестные enum
