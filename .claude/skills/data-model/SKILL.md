# Модель данных

**Вход:** требования / спека / описание сущностей + `project_context.md` (СУБД, владельцы данных).
**Выход:** `outputs/data/<project_id>_<объект>_datamodel_v<N>.md` + ERD
`outputs/diagrams/<project_id>_<объект>_erd_v<N>.puml` + (по запросу или для изменений)
`outputs/data/<project_id>_<объект>_ddl_v<N>.sql` + `trace.md`.

**Крупный** (3+ сущности или изменение существующей схемы) — сначала структура: список
сущностей, связи, сервис-владелец, ключевые допущения. **Малый** (одна таблица, пара полей) — сразу.

## Соглашения по умолчанию

Действуют, если в `project_context.md` не указано иное.

| Аспект | Умолчание |
|---|---|
| СУБД | PostgreSQL |
| Имена | `snake_case`, таблицы в единственном числе (`loan_application`) |
| PK | `id uuid` (генерация на стороне приложения или `gen_random_uuid()`) |
| Время | `timestamptz`, UTC; дата без времени — `date` |
| Деньги | `numeric(15,2)` + `currency char(3)` (ISO 4217); не `float` |
| Статусы / enum | `varchar(32)` + `CHECK` со списком значений; большие и часто меняющиеся справочники — отдельная таблица |
| Технические поля | `created_at`, `updated_at` (NOT NULL); `version int` — если нужна оптимистическая блокировка |
| Удаление | физическое, если нет требования аудита/восстановления; soft delete (`deleted_at`) — только по требованию |
| Внешние ключи | внутри одного сервиса — FK; между сервисами — только ID без FK (у каждого сервиса своя БД) |

Имена полей в API (`camelCase`) и в БД (`snake_case`) различаются — это нормально, маппинг не описывай отдельно, если он механический.

## Алгоритм

1. Прочитай вход, `project_context.md` (кто владелец каких данных!), существующие модели
   в `outputs/data/`.
2. **Сущности и владелец.** Каждая таблица принадлежит одному сервису. Если из требований
   следует, что два сервиса пишут в одну таблицу или читают чужую БД — это архитектурный
   вопрос: подсвети и предложи варианты (событие, API, реплика), не закладывай молча.
3. **Атрибуты.** Для каждого: тип, NULL / NOT NULL, default, ограничения (CHECK, UNIQUE,
   длина), описание, источник (ФТ-ID), признак ПДн. Не выдумывай поля, которых нет в
   требованиях; явно нужные по смыслу (технические поля, FK) — добавляй, остальное — допущением.
4. **Связи и кардинальности**; поведение при удалении родителя (`RESTRICT` / `CASCADE` / запрет удаления).
5. **Индексы** — только под известные запросы: для каждого — какой запрос / ФТ он обслуживает.
   Неизвестные паттерны доступа — открытый вопрос, а не «индекс на всякий случай».
   Уникальные бизнес-ключи и ключи идемпотентности — `UNIQUE`.
6. **Жизненный цикл данных:** статусная модель (ссылка на state-диаграмму), архивация,
   срок хранения, удаление ПДн (152-ФЗ / политика проекта), объём и рост (если известен — для
   партиционирования; если нет — `[TODO]`).
7. **ПДн и безопасность:** какие поля ПДн, маскирование в логах, шифрование — по требованиям
   проекта; без требований — допущение + ОВ.
8. **ERD** по `diagram-generate` (шаблон ERD), **DDL** — если просили или это изменение схемы.
9. **Проверка по Postgres-практикам** (если СУБД — PostgreSQL): загрузи скилл
   `supabase-postgres-best-practices` и прочитай только релевантные `references/`:
   `schema-data-types`, `schema-primary-keys`, `schema-constraints`, `schema-foreign-key-indexes`,
   `query-*-indexes` — для индексов; `lock-*` и `schema-partitioning` — для миграций и больших
   таблиц. Расхождение практики с соглашениями проекта / умолчаниями выше → побеждает проект,
   но риск укажи в «Для ревью». RLS, auth, pg_cron, pgmq — только если они есть в стеке проекта.
10. **Самопроверка:** одно поле — один тип во всех артефактах (спека, API, модель);
   у каждого NOT NULL есть источник значения; у каждого индекса — обоснование.
11. Сохрани, обнови `trace.md` (колонку модели данных добавлять не нужно — укажи файл модели
    в колонке «Спецификация» через `;` или в примечании).

## Изменение существующей схемы

1. Прочитай текущую модель. Составь таблицу изменений с классификацией:

   | Изменение | Класс | Почему |
   |---|---|---|
   | Новая nullable-колонка | 🟢 совместимо | старый код её не знает и не ломается |
   | Новая NOT NULL без default | 🔴 ломает | старые версии сервиса не смогут вставлять строки |
   | Переименование / удаление колонки | 🔴 ломает | читающий код упадёт |
   | Смена типа / сужение длины | 🔴 ломает + риск потери данных | |
   | Новый CHECK / UNIQUE | 🟡 | существующие данные могут не пройти — нужна проверка |

2. Для 🔴 — план **expand → migrate → contract** (без простоя):
   добавить новое рядом → двойная запись / backfill → переключить чтение → удалить старое
   отдельным релизом. Указать, какие шаги — какой релиз.
3. **Backfill существующих строк:** чем заполняется, объём, можно ли батчами, что со
   строками, для которых значение не вычислить.
4. **Откат:** что делать, если релиз откатили после миграции.
5. **Блокировки:** для каждого DDL-шага — какую блокировку берёт и на сколько (по
   `supabase-postgres-best-practices` → `lock-*`): `CREATE INDEX CONCURRENTLY`,
   `ADD CONSTRAINT ... NOT VALID` + `VALIDATE`, `lock_timeout` для миграции.
6. Если изменения затрагивают других потребителей (CDC, отчёты, выгрузки) — предложи `impact-analysis`.
