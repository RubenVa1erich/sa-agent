# Декомпозиция требований

**Вход:** текст задачи / БТ / US (в чате или файл в `inputs/`) + `project_context.md`.
**Выход:** `outputs/requirements/<project_id>_<объект>_reqs_v<N>.md` + обновлённый `trace.md`.
Малый артефакт — структуру не согласовываем, сразу результат.

## Алгоритм

1. **Прочитай** вход и `project_context.md`. Если контекста системы нет совсем и без него
   нельзя понять, какие компоненты затронуты — 1 вопрос. Иначе — допущения.
2. **Выдели бизнес-требования** из входа. Если во входе нет ID — присвой `БТ-NNN`,
   дословно процитировав исходную формулировку.
3. **Определи акторов и затронутые компоненты** (из project_context). Для каждого ФТ
   указывай компонент-исполнитель.
   **Крупное БТ** (затрагивает 3+ компонента или несколько независимо поставляемых
   возможностей) — сначала **карта возможностей**: список модулей «возможность → компонент →
   БТ», каждая независимо тестируема. Покажи её как структуру (`behavior.md`), затем
   декомпозируй по модулям; в документе — раздел «Карта возможностей» перед ФТ.
4. **Декомпозируй на ФТ.** Проходи по сценарию слева направо:
   триггер → валидация входа → проверки прав/состояния → основное действие →
   изменение данных → уведомления/события → ответ. Каждый шаг, где система что-то
   *делает* — кандидат в ФТ. Формулировка по `conventions.md`, атомарно, с AC.
5. **Выдели НФТ** по чек-листу ниже. Только релевантные; каждое — с метрикой или `[TODO]`.
6. **Edge cases** — пройди категории из `quality_bar.md` → «Полнота». Каждый edge case
   либо покрыт AC конкретного ФТ, либо становится отдельным ФТ, либо — открытый вопрос
   («что делать, если...?»).
7. **Конфликты.** Если в `project_context.md` / `trace.md` / `outputs/` есть существующие
   требования по той же сущности — сравни. Противоречия и дубли — в раздел «Конфликты».
8. **Неясности** → `ОВ-NNN` с формулировкой вопроса и адресатом (PM / архитектор / команда X).
9. **Термины.** Сверь термины входа с «Глоссарием» в `project_context.md`: синоним
   существующего термина → используй термин из глоссария; новое доменное понятие → в
   раздел «Новые термины» (термин | значение | источник). В сообщении предложи добавить их
   в глоссарий (`project-init` → «Обновление контекста»), молча не дописывай.
10. **Самопроверка** по `quality_bar.md`. Обнови `trace.md`, включая «Счётчики».

Все номера (БТ, ФТ, НФТ, ОГР, ОВ) — по правилу «Как выдавать номера» из `conventions.md`.

## Режим прожарки

Включает только аналитик. Цель — вытащить требования и пробелы из головы аналитика до
написания документа: лимит «1–2 вопроса» здесь не действует.

1. Прочитай вход, `project_context.md`, `trace.md`, связанные артефакты в `outputs/`.
   **Не спрашивай то, что там уже есть.**
2. Задавай вопросы **сериями по 3–5**, от самых дорогих ошибок к дешёвым:
   границы скоупа → акторы и права → источник истины по данным → статусы и переходы →
   ошибки и отказы зависимостей → конкурентность → НФТ (метрики) → миграция/совместимость.
   Каждый вопрос — конкретный, с вариантами и твоей рекомендацией, где она очевидна.
3. Противоречие с project_context / существующими ФТ / ADR — говори сразу, в серии.
4. Ответ «не знаю» / «уточню» → это ОВ с адресатом, не дави повторно.
5. Конец — когда новые серии не меняют требования, или по слову аналитика («хватит», «пиши»).
   Тогда — обычная декомпозиция (шаги 2–10) с учётом ответов; ответы аналитика — источник
   с пометкой «со слов аналитика, ГГГГ-ММ-ДД».
6. Решения, принятые по ходу, — предложи зафиксировать через `decision-log`; новые термины —
   в «Новые термины». Свой формат ADR и глоссария не заводи.

## Чек-лист НФТ

| Категория | Когда релевантно | Пример метрики |
|---|---|---|
| Производительность | синхронные вызовы, UI | p95 ≤ N мс при M RPS |
| Доступность | клиентские сценарии | SLA 99.9% / мес |
| Надёжность | деньги, внешние вызовы | нет потери данных при рестарте; retry N раз |
| Безопасность | ПДн, деньги, права | авторизация роли X; маскирование полей |
| Аудит | изменения статусов, финопераций | лог: кто, когда, что, было/стало |
| Хранение данных | ПДн, регуляторика | срок хранения N лет; удаление по запросу |
| Масштабируемость | рост нагрузки | линейно до N RPS |
| Наблюдаемость | новые процессы | метрики/алерты на ошибки интеграции |
| Совместимость | изменение API | обратная совместимость для клиентов vN |

## Формат результата

```markdown
# Декомпозиция: <название>
<шапка из artifacts.md>

## Исходные бизнес-требования
| БТ | Формулировка (дословно) | Источник |

## Акторы и затронутые компоненты
- ...

## Функциональные требования
### ФТ-012. <Краткое имя>
**Требование:** Система должна ...
**Компонент:** `<service>`
**Источник:** БТ-003
**Приоритет:** Must
**Критерии приёмки:**
- AC-1: ...
- AC-2: ...

## Нефункциональные требования
| НФТ | Требование | Метрика | Источник | Приоритет |

## Ограничения
| ОГР | Ограничение | Причина |

## Граничные случаи
| # | Ситуация | Ожидаемое поведение | Где покрыто |
|---|---|---|---|
| 1 | Повторный запрос с тем же ключом | вернуть исходный результат | ФТ-012 AC-3 |
| 2 | ... | [TODO] | ОВ-004 |

## Карта возможностей   ← только для крупного БТ
| Возможность | Компонент | БТ | ФТ |

## Конфликты с существующими требованиями
<или «Не обнаружено (проверено: <что>)»>

## Открытые вопросы
| ОВ | Вопрос | Кому | Блокирует |

## Допущения
- ...

## Новые термины   ← если есть
| Термин | Значение | Источник |
```
