# Анализ влияния изменений

**Вход:** описание изменения (CR, новая версия требования) + контекст системы / артефакты проекта.
**Выход:** `outputs/impact/<project_id>_<cr-id|объект>_impact_v<N>.md` + `.confluence.md`.
CR, затрагивающий 2+ компонента — сначала структура (список затронутого), потом полный отчёт.
Полный отчёт по крупному CR пиши по частям (`artifacts.md` → «Запись больших документов»).

## Источники для анализа (в таком порядке)

1. `project_context.md` — компоненты, интеграции, владельцы данных
2. `trace.md` — какие СТ/API/тесты связаны с затронутыми БТ/ФТ (**основной инструмент**:
   иди по цепочке БТ → ФТ → API → диаграммы → тесты)
3. `outputs/` — Grep по именам сущностей, полей, эндпоинтов, событий из CR
   (все формы: `loanAmount`, `loan_amount`, «сумма кредита»)
4. `inputs/` — если аналитик положил туда текущие спеки / контракты / код

Если артефактов проекта мало и trace пуст — честно скажи, что анализ основан на
project_context и описании CR, и список затронутого может быть неполным.
Предложи, какие материалы положить в `inputs/` для полноты.

## Алгоритм

1. **Разбери CR** на атомарные изменения (ИЗМ-1, ИЗМ-2, …): что было → что станет.
2. **Для каждого изменения найди затронутое** (по источникам выше):
   компоненты, эндпоинты/RPC, события/топики, сущности/таблицы/поля, бизнес-правила,
   статусные модели, UI (если известно), отчёты/выгрузки.
3. **Цепочки зависимостей:** кто потребляет изменяемое (потребители API и событий,
   чтение таблицы другими сервисами, отчёты, интеграции с партнёрами). Для каждого —
   сломается / потребует доработки / не затронут.
4. **Классификация** каждого изменения контракта/модели:
   - 🔴 **Ломающее** — существующие потребители перестанут работать без доработки
   - 🟡 **Обратно совместимое** — поведение меняется, но контракт совместим
   - 🟢 **Расширение** — только добавление
   Правила — `api-design/references/*` раздел «совместимость».
5. **Данные:** нужна ли миграция существующих данных; что с сущностями «в полёте»
   (заявки в промежуточных статусах на момент релиза).
6. **Артефакты к обновлению** — конкретные файлы из `outputs/` с тем, что поменять.
7. **Риски** и **план действий**: порядок изменений (сначала провайдер, потом потребители;
   feature toggle; двойная запись/публикация), кого привлечь, что согласовать.
8. Открытые вопросы. Самопроверка.

## Формат отчёта

```markdown
# Анализ влияния: <CR-ID / название>
<шапка из artifacts.md>

## Резюме
<3–5 строк: масштаб, есть ли ломающие изменения, главный риск, рекомендация>

## Изменения
| ИЗМ | Было | Станет | Источник |

## Затронутые элементы
| ИЗМ | Элемент | Тип (компонент/API/событие/таблица/правило) | Характер изменения | Класс 🔴🟡🟢 |

## Цепочки зависимостей
| Изменяемый элемент | Потребитель | Последствие | Требуется |

## Данные и миграция
## Сущности «в полёте»

## Артефакты к обновлению
| Файл | Что изменить | Приоритет |

## Требования
<Новые / изменённые / устаревающие ФТ — с ID. Устаревшие не удалять, а помечать.>

## Риски
| Риск | Вероятность | Влияние | Митигация |

## План действий
1. ...

## Ограничения анализа
<Что не проверено и почему>

## Открытые вопросы
## Для ревью
```

## После отчёта

Предложи: «Обновить затронутые артефакты?» — если да, для каждого создаётся новая
версия `_v<N+1>` соответствующим скиллом; в `trace.md` устаревшие СТ получают статус
«Устарело (CR-...)».
